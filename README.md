# Thinghood Limited Study Platform

This is an experimental, browser-based learning environment that reimagines how educational data is stored and owned. Without a traditional database, it acts as a digital textbook where the institution hosts the curriculum, but the student retains sovereignty over their work.

Rather than submitting answers to a central server, users log in via a GitHub App. The Quarto frontend then uses a static API (mediated by a Cloudflare Worker) to read, write, and version-control problem sets in the student's own private GitHub repository.

This setup supports interactive exercises, stateful feedback loops, and private study groups, all without needing a dedicated backend.

## Architecture

- **Frontend:** Quarto (Static HTML/JS generation)
- **Authentication:** GitHub App Web Flow
- **Serverless Relay & API Gateway:** Cloudflare Workers (Handling OAuth token exchange and secure Cohort proxying)
- **Storage:** Student's personal private GitHub repository (via GitHub REST API)
- **Version Control:** Automated file-level version hashing. The system archives exact snapshots of individual `.html` files when they change into `archive/<topic>/`, preserving the historical context of a student's answer with zero repository bloat.
- **Pedagogy (Zero-Cost Constructivism):** Uses stateful DOM interpolation to pull old answers forward into future prompts, forcing students to defend their own axioms without relying on centralized databases or LLM validation.
- **Seasonal Cohorts:** A static, file-based community hub where students can publish solutions and engage in peer review via a central repository, without relying on external issue trackers or discussion boards.

## GitHub Usage

Because this application operates without a traditional backend database, all user data (problem set solutions, active state) is saved directly to the student's personal GitHub account via the GitHub REST API.

This architecture mandates strict adherence to the **Principle of Least Privilege** to protect the student's private code repositories from accidental overwrites or malicious data extraction.

### The Security Mechanism: GitHub Apps vs. OAuth Apps

Historically, static applications attempting to write to GitHub relied on **OAuth Apps** requesting the `repo` scope.

- **The Danger of OAuth:** The standard `repo` scope grants an application _full read and write access to every single private repository the user owns_. Storing an OAuth token with the `repo` scope in a browser's `localStorage` is a massive Cross-Site Scripting (XSS) vulnerability. If compromised, an attacker could wipe a student's entire GitHub ecosystem.

To eliminate this vulnerability, this curriculum strictly uses a **GitHub App**.

- **The GitHub App Sandbox:** When a student authenticates, they are installing a GitHub App. During installation, GitHub explicitly forces the user to designate **exactly one repository** for the application to access.
- **Scope Restriction:** The access token generated by the Serverless Relay is cryptographically scoped exclusively to the Installation ID tied to that single repository. It is structurally prevented from accessing any other repository on the student's account.

### Automated Repository Discovery

Even with restricted access, relying on students to type the name of the designated repository into a text prompt can result in accidental data injection (e.g., if they accidentally type the name of an existing work project, the app might inject curriculum files into it).

To resolve this, our client-side JavaScript (`js/github-sync.js`) uses the **GitHub Installations API** (`/user/installations`). When a student logs in:

1. The app automatically queries GitHub to find where the app was installed.
2. It targets that repository automatically.
3. The student never types a repository name, eliminating accidental path overwrites entirely.

### Serverless Relay & API Gateway

Client-side JavaScript cannot securely hold the GitHub App's `CLIENT_SECRET` (which is required to exchange an OAuth code for an Access Token), nor can it enforce strict path boundaries when writing to a centralized community repository.

To resolve this, the architecture utilizes an isolated **Cloudflare Worker** that serves two critical purposes:

1. **OAuth Relay:** It holds the `CLIENT_SECRET` securely in its environment variables, receives the temporary `code` from the frontend, validates it against GitHub, and returns the short-lived access token to the browser.
2. **Cohort API Gateway:** It acts as a secure proxy for the seasonal cohorts. It enforces strict repository and path constraints (`cohort_data/{topic}/{cohortId}/{problemId}`), cryptographically binds the user's GitHub identity to their submissions, performs atomic fetch-and-merge operations for cohort data, and enforces conditional writes using SHA locking to prevent stale overwrites.

- **Spam Prevention:** The Cloudflare worker implements an in-memory IP rate limiter to prevent automated scripts from draining the daily free tier allowance.

## Setup and Deployment

### 1. Build the Quarto Site

Execute the following to render the static HTML site:
\`\`\`bash
quarto render
\`\`\`
Host the generated `_site` directory on GitHub Pages or any static hosting provider.

### 2. Configure the GitHub App

- Register a new GitHub App in Developer Settings.
- Set the Homepage and Callback URLs to your deployed Quarto site.
- Request **Read & Write** permissions for **Contents**.
- Uncheck "Active" for Webhooks (they are not used).

### 3. Deploy the Cloudflare Worker Relay

- Deploy the script found in `scripts/cloudflare-worker.js` to a Cloudflare Worker.
- Bind your `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` as environment variables.
- Update `SYNC_CONFIG` inside `js/github-sync.js` with the Worker's URL and your Client ID.
